# 2.2 非目标

- ~~仅注入渲染层——编号必须在原始 Markdown 中可见~~ **已翻案（2026-09-25 定案，见 [3.22](./3.22-虚拟编号模式.md)）**：
  「仅显示」的虚拟编号模式与「写入文件」模式**并列**，是本插件的第二种哲学，不是替代。粒度跟着路径
  规则走（每条规则可单独选）；新安装默认「仅显示」，老用户保持「写入」。翻案理由：写入文件的 U+2060
  标记是重度用户的信任成本，虚拟模式从根上消除它（零 WJ、编号引发的断链整体消失、阅读视图天然支持）；
  竞品（Heading Keeper 默认虚拟、Number Suite、gurjar1、Heading Decorator）已验证这条路。「写入」
  服务的场景（外部编辑器 / GitHub / Publish 里也要看到编号）不变，继续由写入模式承担。
  仍不做的是 CSS 计数器这类**脱离编号引擎**的渲染：虚拟编号与写入编号共用同一个 `numberHeadings`，
  模板、白名单、`<!-- skip -->`、层级范围语义完全一致
- **改写用户的标题层级**（插件只增删编号前缀，绝不把 `#` 改成 `##`；多个 H1 的"规整"交给用户/白名单）
- ~~生成目录~~ **决策已翻案（0.7.28，见 [3.16](./3.16-原生风格TOC-burn-in.md)）**：单文件内的目录不再是
  非目标——burn-in 真实 Markdown 文本这件事，Dataview（渲染层，依赖额外插件才能看）与 Table of
  Contents 插件（一次性插入静态文本，标题改了不会跟着更新）都做不到，与本插件"写入真文本、不做渲染
  覆盖层"的核心哲学一致，理由与 Backlink 同步（同样是"别的插件做不到"）同源。**跨文件聚合视图**（总
  索引、跨笔记聚合）仍是非目标，继续走 Roadmap M9「Dataview 集成」路线——单文件目录与跨文件聚合视图
  是两个不同范围的问题，互不替代
- 在 frontmatter 中存储任何**配置**（模板、白名单、路径规则刻意排除，以保持笔记整洁）；frontmatter 仅用作单文件开关
- 多文件批量重新编号（后续版本）
- Git 感知最小化差异（后续版本）
- 标题居中 / 自定义字体等**渲染层美化**（与「burn-in 写入」哲学冲突，明确不做；有此需求可用 Auto Heading）
